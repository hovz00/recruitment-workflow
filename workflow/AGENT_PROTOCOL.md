# Recruitment Workflow 协议

本协议是本项目的统一招聘工作流行为规范。Codex、Claude Code、Cursor 等工具只通过各自的入口文件进入本协议；岗位文件、Excel 台账、候选人档案和操作日志是长期状态，不依赖聊天历史。

## 1. 启动与当前岗位

收到招聘相关请求后，先读取本文件和 `00-招聘规则.md`。每个新对话执行 `create-session.mjs --root <根目录>`，保存返回的会话编号；用户明确继续某个已有会话时才复用其编号。对话上下文压缩或重开工具时保留/恢复该编号，不要重新生成并猜测上一个岗位。

当前岗位保存于 `.recruitment-agent/sessions/<会话编号>/current-role.json`。切岗、新建岗位、标准确认、候选人预览与执行、身份关联预览与执行，以及岗位快照都传相同的 `--session`。指定会话但没有岗位时不会回退到全局当前岗位：

- 用户明确提到岗位时，先核对 `workflow/roles/<岗位名称>/` 存在，再切换当前岗位；
- 用户说“继续上次招聘”或未指明岗位时，使用当前岗位；没有当前岗位时，只询问岗位名称或是否新建岗位；
- 确认当前岗位后，读取该岗位的 `CONTEXT.md`、`ROLE_STANDARD.md`、`PIPELINE.json`、`SOURCING_STRATEGY.md`、`candidate-ledger.xlsx` 和 `ACTION_LOG.md`；
- 每次准备写入前，展示岗位与候选人，防止写错目录。

使用 `get-role-snapshot.mjs` 汇总岗位标准版本、流程中人数、到期跟进、缺少下一步动作、待补面试反馈、最近操作和最近看板同步。

旧岗位缺少字段、ACTION_LOG.md 或 candidates 目录时，使用 `migrate-role-workspace.mjs` 迁移，不要重复初始化。命名会话写入遇到 writer.lock 最多等待 5 秒；超时先确认另一写入是否仍在运行，只有确认原进程已退出、锁为残留时才移除该锁并重试。锁等待不会自动删除别人的锁。

旧调用不传 `--session` 时仍使用 `.recruitment-agent/current-role.json`，仅用于单对话兼容；不得在同一对话混用命名与全局状态。会话隔离是防止操作串岗的本地机制，不是账号认证或文件访问权限隔离。[完整命令与恢复步骤](../docs/SESSIONS-AND-TALENT.md)。

## 2. 意图路由

| 用户表达 | 处理方式 |
| --- | --- |
| 新建岗位、提供 JD、澄清需求 | 使用 `recruit-grill`；岗位标准与流程确认后再初始化岗位目录。 |
| 评估简历、内推或附件 | 使用 `resume-evidence-review`；先确认来源、收取日期和重复候选人。 |
| 电话沟通记录 | 读取候选人档案与电话模板，整理事实、补充证据和下一步。 |
| 面试反馈、决策会结论 | 使用 `feedback-calibration`，区分流程事实、能力反馈、岗位级观察和待澄清事项。 |
| Offer、入职或候选人进展 | 根据 `PIPELINE.json` 生成变更预览。 |
| 更新搜寻、人才盘点 | 读取寻源策略与关键词迭代表，只记录有依据的观察。 |
| 跨岗位重复投递、推荐、身份核实 | 查询本地人才关联及同名申请；目标岗位独立评估，经确认后关联或解除身份。 |
| 复盘、同步看板、待办 | 读取岗位快照，并从台账同步 `招聘数据复盘.html`。 |

一次只提出一个必要的澄清问题。材料没有明确写出的内容统一标为 **待核实**。

新建岗位时，先展示并确认完整岗位文档和流程，再将 Markdown 文档以文件名到全文的 JSON 映射传给初始化脚本 `--documents`，并通过 `--confirmation` 传入真实确认得到的 `version`、`confirmedBy`、`evidence`。未提供的文档是草稿，不能把模板版本号当作已经确认的岗位标准。

候选人提案要求有效的 `ROLE_CONFIRMATION.json`，且其摘要必须与当前 `ROLE_STANDARD.md`、`PIPELINE.json` 一致。旧岗位或标准变更后，先核对完整文档，收到招聘者明确确认，再执行 `confirm-role-standard.mjs`；不得自行补造确认。常规上下文/日志追加不改变标准确认。

## 3. 阶段和候选人规则

- 主阶段记录候选人已经实际到达的流程节点；阶段状态仅使用 `进行中`、`通过`、`终止`。
- “暂缓”“待回复”“约面”等写入备注、下一步动作或下次跟进日期。
- “一面通过，待安排二面”写为“一面｜通过”，下一步为“安排二面”；二面时间已明确约定后，才写为“二面｜进行中”。
- 候选人更新优先以候选人 ID 精确定位；姓名仅作辅助核对。姓名重复、ID 与姓名不一致、岗位不清晰或流程不合法时停止并询问。
- 同名且明确核实为不同人后，新建提案可包含 `identityResolution: { confirmedDistinct: true, matchedCandidateIds: [...全部同名ID], reason: "核实依据" }`；预览展示匹配对象和依据，确认后才新增。禁止改名绕过查重；匹配范围不全、旧人缺ID或ID重复时先核实修正。
- 年龄、学历和工作年限仅按 `ROLE_STANDARD.md` 中已确认的规则呈现；不得自行推断。
- 新增候选人必须有来源、简历收取日期、阶段、状态；未知收取日期先澄清。日期使用有效的 YYYY-MM-DD。
- 本轮面试反馈摘要以 `[编号-阶段名]` 标记适用轮次，例如 `[2-业务一面]`；旧轮次摘要不能抵消当前轮次的反馈待办。
- 固定的一面日期等用于约面安排；动态的 `编号-阶段名日期` 和 `编号-阶段名通过日期` 只记实际发生且已确认的进入 / 通过日期。Offer 接受日期与预计入职日期分别记录，不补造历史。
- 自定义面试在 PIPELINE 中设置 `kind: "interview"`，用 `appointmentField` 明确预约字段；默认是 `编号-阶段名预约日期`。非面试阶段可用 `kind: "process"`。缺列先迁移；预约日期与历史日期不能混用。
- 来源、收取日期、阶段、状态不能在更新中清空；得分0–10、覆盖率0–100，空值表示未知。历史日期需符合已知前后关系且不能在未来；未来约面和跟进使用预约字段。

## 4. 变更预览与确认

自然语言只用于理解。任何写入前，先生成一份本地待确认提案，包含岗位、候选人、字段修改前后、依据和提案编号。普通用户只看到简洁预览，例如：

```text
当前岗位：AI 产品经理
候选人：张某

准备更新：
- 阶段状态：进行中 → 通过
- 下一步动作：安排二面

确认写入吗？
```

只有“确认”“确认写入”“按这个更新”“执行”“可以更新台账”视为确认。用户补充字段后，先更新预览，不能直接执行旧提案。待确认提案保存在 `.recruitment-agent/pending-actions/`；同一会话、同一岗位的新预览使旧预览失效。提案绑定创建会话，其他会话不能执行；同一岗位台账变化时，各会话的旧预览都需要重新生成。用户意图不明确时先重新展示预览。

候选人变更由下述确认脚本执行。岗位规则、寻源策略和关键词文档的后续修改不属于候选人提案：先展示文档差异、适用范围和新版本，经招聘者确认后由 AI 文件工具保存，并在 ACTION_LOG.md 追加依据。不得宣称这类文档修改由候选人脚本自动完成。

其中岗位标准或流程变更后，还需记录标准确认。旧预览即使只修改评分，也不能继续执行。提案中的 `standardVersion` 用于展示本次依据，执行时会核对确认记录与文档摘要。

## 5. 确定性写回

确认后使用 `apply-confirmed-action.mjs`：

1. 再次读取 Excel，校验提案中的修改前值仍一致；
2. 校验标准确认、字段白名单、完整记录的必填项、流程状态、数值范围和日期先后；
3. 写入 `candidate-ledger.xlsx`、`candidates/<候选人ID>.md`、`CONTEXT.md` 与 `ACTION_LOG.md`；
4. 同步 `招聘数据复盘.html`；
5. 任一环节失败时恢复备份，并保留待确认提案，报告失败原因。

`ACTION_LOG.md` 只能追加，不能覆盖历史。

不要使用旧版 `update-candidate-ledger.mjs` CLI 绕过确认写回。预览和复盘使用同步脚本；需要手动上传时调用 `export-review-data.mjs` 生成标准 XLSX / CSV，不能直接上传操作台账。默认去标识化明细，只有明确的内部明细需求才使用 `--privacy internal`。手动上传仅影响当前预览，不写回台账。

## 6. 跨岗位身份关联

新增预览中的 `crossRoleMatches` 只表示其他岗位有同名记录，不表示已确认是同一人。`crossRoleMatchIssues` 非空表示查询不完整，须提示并核实，不得说“已查重无重复”。普通候选人预览会显示这些本地核对结果，调用者提供的同名列表不能覆盖查询结果。

使用 `query-talent.mjs` 按姓名或岗位/候选人ID查询。同一人申请多个岗位时，每个岗位仍有独立申请和证据。核实本人身份、目标岗位意愿与适用材料后，先按目标岗位规则建立申请，再通过 `create-identity-proposal.mjs` 生成关联预览；`apply-identity-proposal.mjs` 仅在招聘者确认后执行。`link` 要求 `confirmedSamePerson: true`、实际确认人和依据；`unlink` 用于纠正误关联，也要展示完整受影响申请并确认。

跨岗推荐用 `relationship: "referral"` 记录来源和目标；并行申请用 `parallel`。不自动终止原岗位、不沿用原评分或面试通过结论、不自动联系候选人。一个统一人才身份在同一岗位只能关联一个候选人 ID；合并涉及冲突时先核实，不能覆盖其中一条。

身份提案绑定当前会话、索引和受影响台账/日志/档案摘要，事实变化后需重新预览。执行保存本地 `talent-registry.json`，并追加受影响岗位日志和档案；失败则恢复备份。关联与解除均保留事件记录，复盘导出不包含人才索引。查询中的去重人数仅按已确认关联计算，未核实申请暂计为不同人；不能称为已完全去重的真实人数。

## 7. 人工边界

AI 可整理材料、定位证据、提示缺口、生成草稿和运行本地确定性脚本。AI 不得抓取招聘平台、自动联系候选人、自动约面、自动拒绝、自动淘汰、自动录用或自行修改岗位标准。所有不可逆动作必须经过招聘者确认。
